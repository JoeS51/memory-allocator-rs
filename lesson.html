Build a Bump Allocator

A guided, pencil-first lesson. You will derive the allocator one invariant at a time, test it, and only reveal complete code when you are genuinely stuck.

00

Before takeoff

Your briefing

You are going to manage one fixed region of memory. Each allocation moves a cursor forward. You will not replace Rust's global allocator, request pages from the operating system, or recycle individual allocations yet.

Time90-150 minutes
ToolsEditor, terminal, Rust

How to use this lesson

  1. Read one chapter, then close the browser or scroll away.
  2. Implement the checkpoint in src/lib.rs from memory.
  3. Use the first hint only after ten focused minutes.
  4. Use the solution only after you can explain what is blocking you.
  5. Run cargo test checkpoint_N after each checkpoint, replacing N with its number.
Scope boundary This is an arena-style allocator for learning. It obtains a byte buffer from its caller and sub-allocates from it. Production allocators also acquire memory from an operating system, handle concurrency, and usually reuse freed blocks.

Prerequisite check

You should recognize structs, methods, Option, arrays, and basic tests. Raw pointers are taught here. No allocator knowledge is assumed.

01

Mental model

Memory is an addressed byte array

Imagine that the caller lends your allocator 16 bytes. Every byte has an address. The allocator does not care whether future users interpret those bytes as an integer, a struct, or text. It only answers: where can this many properly aligned bytes fit?

0123 4567 891011 12131415

The orange underline is next, the offset of the first unused byte.

After allocating 5 bytes, offsets 0..5 are occupied and next == 5.

0123 4567 891011 12131415

The central invariant

0 <= next <= capacity

bytes before next: reserved
bytes at/after next: available

An invariant is a statement that must remain true before and after every public operation. Most allocator bugs are invariant violations disguised as arithmetic.

Checkpoint: simulate by hand

Start with 16 bytes and next = 0. Ignore alignment for now. Calculate the returned range and new cursor for requests of 3, 6, and 8 bytes.

Hint 1
The returned range is next..next + size.
Reveal answer

The first two succeed: 0..3, then 3..9. The final request needs 9..17, which does not fit, so it fails and next remains 9.

Checkpoint: implement numeric allocation

  • new starts at offset zero.
  • allocate returns the reserved range.
  • A request beyond capacity returns None.
  • A failed request must not move next.
  • Do not use ordinary next + size.
Hint 1: why ordinary addition is wrong

usize can overflow. Debug builds panic; optimized builds can wrap to a small number. Use checked_add, whose failure is already represented by None.

Hint 2: control flow
let end = self.next.checked_add(size)?;
if end > self.capacity {
    return None;
}
Reveal implementation
impl Cursor {
    fn new(capacity: usize) -> Self {
        Self { capacity, next: 0 }
    }

    fn allocate(&mut self, size: usize) -> Option<Range<usize>> {
        let start = self.next;
        let end = start.checked_add(size)?;
        if end > self.capacity {
            return None;
        }

        self.next = end;
        Some(start..end)
    }
}

Write one test that succeeds twice, then fails. Also assert that the cursor did not move after failure.

03

Hardware constraint

Addresses need alignment

Many values must begin at an address divisible by a particular power of two. A u8 has alignment 1, a u32 commonly has alignment 4, and a u64 commonly has alignment 8.

RequestValid start examplesInvalid start examples
alignment 10, 1, 2, 3none
alignment 40, 4, 8, 121, 2, 3, 5
alignment 80, 8, 16, 244, 10, 20

If next == 5 and the next request needs alignment 4, bytes 5, 6, and 7 become padding. Allocation starts at 8.

0123 4padpadpad 891011 12131415

The rounding formula

For power-of-two alignment, the next aligned address is:

mask = alignment - 1
aligned = (address + mask) & !mask

The mask's low bits are all ones. Adding it rounds upward; clearing those low bits rounds down to the required boundary. Use checked addition so rounding cannot overflow.

Checkpoint: write align_up

fn align_up(address: usize, alignment: usize) -> Option<usize> {
    todo!()
}

Requirements: assert that alignment is a power of two, use checked arithmetic, and return the first aligned address greater than or equal to the input.

Test at least (5, 4) -> 8, (8, 4) -> 8, and (usize::MAX, 8) -> None.

Hint 1: Rust helpers

alignment.is_power_of_two() checks the precondition. !mask flips every bit in the mask.

Reveal implementation
fn align_up(address: usize, alignment: usize) -> Option<usize> {
    assert!(alignment.is_power_of_two());
    let mask = alignment - 1;
    address.checked_add(mask).map(|value| value & !mask)
}
Important Align the actual memory address, not merely the offset. If the buffer begins at address 1003, offset 0 is not aligned to 8 even though zero is divisible by 8.
04

Own the region, not its values

Borrow uninitialized storage

The caller will create a fixed byte array. Your allocator borrows it exclusively and remembers its start address, capacity, and cursor.

use std::{
    alloc::Layout,
    marker::PhantomData,
    mem::MaybeUninit,
    ptr::NonNull,
};

struct Bump<'a> {
    start: NonNull<u8>,
    capacity: usize,
    next: usize,
    _memory: PhantomData<&'a mut [MaybeUninit<u8>]>,
}

What each unusual type means

  • MaybeUninit<u8>: storage that does not claim to contain a valid value yet.
  • NonNull<u8>: a raw pointer known not to be null. It is still not automatically safe to dereference.
  • PhantomData<&'a mut ...>: tells Rust that Bump exclusively borrows the memory for lifetime 'a, even though the struct stores only a raw pointer.
  • Layout: a standard pair of size and alignment used by Rust's allocation APIs.

Convert memory.as_mut_ptr() from a pointer to MaybeUninit<u8> into a pointer to u8 with .cast(). Store the slice length and initialize the cursor.

Hint 1: making NonNull

NonNull::new(pointer) returns an Option. Slice pointers are non-null, including the special dangling pointer used by empty slices, so an expect here documents that invariant.

Reveal implementation
impl<'a> Bump<'a> {
    fn new(memory: &'a mut [MaybeUninit<u8>]) -> Self {
        let start = NonNull::new(memory.as_mut_ptr().cast::<u8>())
            .expect("slice pointers are never null");

        Self {
            start,
            capacity: memory.len(),
            next: 0,
            _memory: PhantomData,
        }
    }

    fn used(&self) -> usize { self.next }
    fn capacity(&self) -> usize { self.capacity }
}

The core operation

Turn a layout into a pointer

The algorithm is short, but its order matters. Work in actual addresses while aligning, then convert the aligned address back to an offset.

fn allocate(&mut self, layout: Layout) -> Option<NonNull<u8>> {
    // 1. Decide what zero-sized requests mean.
    // 2. Calculate the address at the cursor.
    // 3. Round that address up to layout.align().
    // 4. Convert the aligned address back to an offset.
    // 5. Calculate the end offset and check capacity.
    // 6. Produce the pointer and commit the new cursor.
    todo!()
}

Checkpoint: implement allocation

For this project, reject layouts with size zero. Real allocator interfaces define special rules for zero-sized types; explicitly excluding them keeps this first contract small.

Every addition and subtraction derived from addresses should be checked. Do not update next until every check has passed.

Hint 1: derive the numbers
let base = self.start.as_ptr() as usize;
let current = base.checked_add(self.next)?;
let aligned = align_up(current, layout.align())?;
let start_offset = aligned.checked_sub(base)?;
let end = start_offset.checked_add(layout.size())?;
Hint 2: the one unsafe operation

After proving that start_offset lies inside the buffer, calculate the pointer with:

let pointer = unsafe { self.start.as_ptr().add(start_offset) };

add is unsafe because Rust cannot prove the result remains in the same allocation. Your preceding bounds check is the proof.

Reveal implementation
fn allocate(&mut self, layout: Layout) -> Option<NonNull<u8>> {
    if layout.size() == 0 {
        return None;
    }

    let base = self.start.as_ptr() as usize;
    let current = base.checked_add(self.next)?;
    let aligned = align_up(current, layout.align())?;
    let start_offset = aligned.checked_sub(base)?;
    let end = start_offset.checked_add(layout.size())?;

    if end > self.capacity {
        return None;
    }

    // start_offset..end was proven to lie inside the borrowed buffer.
    let pointer = unsafe { self.start.as_ptr().add(start_offset) };
    self.next = end;
    NonNull::new(pointer)
}

Why there is no deallocate

A bump allocator cannot reclaim one middle block without tracking more metadata. Its superpower is that allocation is almost only arithmetic. Its cost is that memory is reclaimed all at once.

/// All previously returned pointers must no longer be used.
unsafe fn reset(&mut self) {
    self.next = 0;
}

reset is unsafe because it allows future allocations to reuse the same bytes. Reading or writing through an old pointer afterward could access a different object. Reset also does not run destructors.

06

Crossing the boundary

Write through the returned pointer

Your allocator returns storage, not a Rust value. To place a u32 there, request its layout, cast the byte pointer, and initialize the memory.

fn main() {
    let mut memory = [MaybeUninit::<u8>::uninit(); 64];
    let mut bump = Bump::new(&mut memory);

    let slot = bump
        .allocate(Layout::new::<u32>())
        .expect("enough room")
        .cast::<u32>();

    unsafe {
        slot.as_ptr().write(42);
        println!("stored: {}", slot.as_ptr().read());
    }
}

Write the safety argument before the unsafe block

An unsafe block is not permission to ignore rules. It is a claim that you checked rules the compiler could not check.

  • The pointer is aligned for u32 because it came from Layout::new::<u32>().
  • At least size_of::<u32>() bytes are inside the borrowed buffer.
  • write initializes those bytes before read reads them.
  • No reset or overlapping allocation occurs while the pointer is used.
  • u32 has no destructor that needs to run.
Pointer lifetime NonNull does not carry a Rust lifetime. The compiler cannot prevent use after the backing buffer or allocator is gone. Dereferencing the pointer is unsafe precisely because the programmer must verify that it is still valid.

Checkpoint: allocate two values

Allocate a u8, then a u64. Write values to both and print them. Before running, predict whether padding will be needed; the answer depends on the buffer's actual starting address.

Hint

Use Layout::new::<T>(), then .cast::<T>(). Keep all pointer writes and reads in an unsafe block after allocation succeeds.

Reveal example
let byte = bump.allocate(Layout::new::<u8>()).unwrap().cast::<u8>();
let wide = bump.allocate(Layout::new::<u64>()).unwrap().cast::<u64>();

unsafe {
    byte.as_ptr().write(7);
    wide.as_ptr().write(9001);
    println!("{} {}", byte.as_ptr().read(), wide.as_ptr().read());
}
07

Attack the invariant

Test what can go wrong

Allocator tests should focus on addresses and boundaries, not just stored values. Write these tests yourself before revealing the versions below.

Checkpoint: four failure-focused tests

  1. Exhaustion: exactly fill an 8-byte buffer, then ensure one more byte fails.
  2. Alignment: allocate one byte, then allocate a u64 layout and inspect the returned address.
  3. No overlap: allocate two 4-byte layouts and compare their address ranges.
  4. Reset: allocate, reset, and show that used bytes return to zero.
Reveal tests
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn reports_exhaustion_without_moving_cursor() {
        let mut memory = [MaybeUninit::<u8>::uninit(); 8];
        let mut bump = Bump::new(&mut memory);
        let eight_bytes = Layout::from_size_align(8, 1).unwrap();

        assert!(bump.allocate(eight_bytes).is_some());
        assert_eq!(bump.used(), 8);
        assert!(bump.allocate(Layout::new::<u8>()).is_none());
        assert_eq!(bump.used(), 8);
    }

    #[test]
    fn honors_requested_alignment() {
        let mut memory = [MaybeUninit::<u8>::uninit(); 32];
        let mut bump = Bump::new(&mut memory);

        bump.allocate(Layout::new::<u8>()).unwrap();
        let pointer = bump.allocate(Layout::new::<u64>()).unwrap();

        assert_eq!(pointer.as_ptr() as usize % std::mem::align_of::<u64>(), 0);
    }

    #[test]
    fn allocations_do_not_overlap() {
        let mut memory = [MaybeUninit::<u8>::uninit(); 16];
        let mut bump = Bump::new(&mut memory);
        let layout = Layout::from_size_align(4, 1).unwrap();

        let first = bump.allocate(layout).unwrap().as_ptr() as usize;
        let second = bump.allocate(layout).unwrap().as_ptr() as usize;

        assert!(first + 4 <= second);
    }

    #[test]
    fn reset_reclaims_all_memory() {
        let mut memory = [MaybeUninit::<u8>::uninit(); 16];
        let mut bump = Bump::new(&mut memory);

        bump.allocate(Layout::new::<u32>()).unwrap();
        assert!(bump.used() > 0);

        // No returned pointer is used after this point.
        unsafe { bump.reset() };
        assert_eq!(bump.used(), 0);
        assert_eq!(bump.capacity(), 16);
    }
}

Emergency reference

Complete implementation

Do not open this first. Use it to compare decisions after your implementation works, or to recover if you are fully blocked.

Reveal complete allocator and demonstration
use std::{
    alloc::Layout,
    marker::PhantomData,
    mem::MaybeUninit,
    ptr::NonNull,
};

fn align_up(address: usize, alignment: usize) -> Option<usize> {
    assert!(alignment.is_power_of_two());
    let mask = alignment - 1;
    address.checked_add(mask).map(|value| value & !mask)
}

struct Bump<'a> {
    start: NonNull<u8>,
    capacity: usize,
    next: usize,
    _memory: PhantomData<&'a mut [MaybeUninit<u8>]>,
}

impl<'a> Bump<'a> {
    fn new(memory: &'a mut [MaybeUninit<u8>]) -> Self {
        let start = NonNull::new(memory.as_mut_ptr().cast::<u8>())
            .expect("slice pointers are never null");

        Self {
            start,
            capacity: memory.len(),
            next: 0,
            _memory: PhantomData,
        }
    }

    fn allocate(&mut self, layout: Layout) -> Option<NonNull<u8>> {
        if layout.size() == 0 {
            return None;
        }

        let base = self.start.as_ptr() as usize;
        let current = base.checked_add(self.next)?;
        let aligned = align_up(current, layout.align())?;
        let start_offset = aligned.checked_sub(base)?;
        let end = start_offset.checked_add(layout.size())?;

        if end > self.capacity {
            return None;
        }

        // The checked range start_offset..end is within the borrowed buffer.
        let pointer = unsafe { self.start.as_ptr().add(start_offset) };
        self.next = end;
        NonNull::new(pointer)
    }

    fn used(&self) -> usize {
        self.next
    }

    fn capacity(&self) -> usize {
        self.capacity
    }

    /// The caller must never use previously returned pointers after reset.
    unsafe fn reset(&mut self) {
        self.next = 0;
    }
}

fn main() {
    let mut memory = [MaybeUninit::<u8>::uninit(); 64];
    let mut bump = Bump::new(&mut memory);

    let slot = bump
        .allocate(Layout::new::<u32>())
        .expect("enough room")
        .cast::<u32>();

    unsafe {
        slot.as_ptr().write(42);
        println!("stored: {}", slot.as_ptr().read());
    }

    println!("used {} of {} bytes", bump.used(), bump.capacity());
}

Can you explain every line?

  1. Why is the buffer made of MaybeUninit<u8>?
  2. Why do we align base + next rather than only next?
  3. Why is checked_add part of correctness, even with a small buffer?
  4. Why is pointer add unsafe while integer addition is not?
  5. Why must cursor mutation happen last?
  6. What becomes invalid after reset?
  7. Why can this allocator leak resources held by values with destructors?
Reveal short answers
  1. The bytes begin without initialized Rust values.
  2. Alignment constrains real addresses, and the buffer's base may itself be unaligned for the request.
  3. Address arithmetic can overflow independently of logical capacity.
  4. Creating an out-of-bounds pointer violates Rust's pointer rules; the compiler cannot prove the bounds from a raw pointer.
  5. A failed operation must leave the allocator invariant unchanged.
  6. Every pointer returned before reset; future allocations may reuse those bytes.
  7. Reset forgets bytes, not typed values, and therefore cannot discover or run their Drop implementations.
09

After landing

Next missions

Do these in order. Each introduces one new systems idea without turning the project into a production allocator.

  1. High-water mark: track the maximum value of next to measure peak memory usage.
  2. Typed allocation: add allocate_value<T>. Decide who runs T::drop and document the contract before coding.
  3. Scoped arena: make it impossible for safe references to survive reset by tying them to a closure or scope.
  4. Downward bumping: start at capacity and move toward zero. Compare alignment arithmetic.
  5. Free list: add metadata that can reuse individual blocks. This is a different allocator design, not a small bump-allocator feature.
  6. GlobalAlloc study: read std::alloc::GlobalAlloc and identify requirements this toy does not meet before trying to implement it.
Definition of done You are finished when the tests pass and you can reconstruct the core algorithm from the invariant: align the current address, check the complete range, then commit the cursor.

Pocket glossary

ArenaA memory region from which many objects are allocated and later reclaimed together.
AlignmentA requirement that an address be divisible by a particular power of two.
LayoutA size and alignment pair describing an allocation request.
Raw pointerAn address without Rust's automatic borrow and lifetime checks.
PaddingUnused bytes skipped to reach a valid aligned address.
FragmentationWasted memory caused by unusable gaps or rounding. This allocator has alignment waste but no reusable holes.
Undefined behaviorBreaking language rules in a way that removes all guarantees, such as dereferencing an invalid or misaligned pointer.
